# 网关双道调度器：为什么能优化并发、怎么优化

日期：2026-11-14（北京） 代码：`rag-proxy/rag_proxy.py`

## 1. 现状与问题

对外入口 `rag-proxy:8080` 后面是两条独立 lane：

| 道 | 端口 / 卡 | 引擎 | 批槽 | 定位 |
|---|---|---|---|---|
| 快道 | 8091 / GPU0 | 0.1.59.1 + unified | 4 | 低延迟、长上下文、实验 |
| 普道 | 8092 / GPU1 | 0.1.59.1 + unified | 4 | 主力流量、短请求 |

改动前的路由（`route_upstream`）：

- 模型 ID **死钉**：`qwen3.8-flash-fast`/`strata-a` → 8091，`qwen3.8-flash`/`strata-b` → 8092；
- 未指定模型：普道优先，普道"满"才溢出快道；
- 没有高峰预留、没有按实时负载选择。

**问题**：引擎的并发上限是每条 lane 4 个批槽，但请求被钉死在一条道上时会出现
「一条道排队、另一条空转」：

- 快道请求在 8091 排第 5 位时，8092 可能 4 个槽全空；
- 普道流量把 8092 排满时，8091 空着也不会接；
- 反过来，普道的长 prompt 也常占着快道（历史上快道被常规流量压满，才加过"慢道优先"）。

引擎侧还有一个硬约束（[[strata-concurrency-limits]]）：**prefill 单线程串行**，一个 prompt 读完才读下一个；
解码 94% 时间在等主机专家。所以「排队长度」直接决定 TTFT——排队从 4 条变成 8 条可用的槽池，
第 5 条就不再等第二轮。

实测支撑（2026-11-14 静默窗口，同规格 262144 上下文、唯一前缀、1200 token 提示）：

| 部署 | 4 路聚合 | 8 路聚合 | 8 路 TTFT |
|---|---|---|---|
| 两条 lane（4+4） | 107.8 | **141.6 tok/s** | 1.69 s |
| 单卡合并（8 槽） | 110.6 | 107.7 tok/s | 2.28 s |

结论：**两条 lane 合起来有 8 个批槽，是这台机器并发能力的上限**。调度器的任务就是把这 8 个槽
按用户语义（快/普）和实时占用尽量填满，同时不让快道被普道挤占。

## 2. 数据：什么时候快道用得多

`~/logs/infer.db`（rag-proxy 全量请求元信息，14 天，北京时间）：

- 快道每小时 100–550 条，普道 5.4–6.4k 条；
- 快道**并发**（按请求区间重叠计算）峰值 26；按小时看快道独占一个槽以上的时间占比：
  - 09–12 点：≥1 并发 81–90%，**≥4 并发（4 槽全满）占 61–66%**；
  - 23–01 点：≥1 并发 77–79%，≥4 占 10–23%；
  - 06–07 点：≥4 占 32–44%；
  - 其余时段 ≥4 普遍 < 20%。

据此配置**分时预留**（快道上留给快道请求的槽数）：

```json
"reserve_by_hour": {"9":3,"10":3,"11":3,"12":3,"23":2,"0":2,"1":2,"6":2,"7":2}
```

即 09–12 点普道最多只能用快道 1 个槽（4−3），其余时段最多 2 个槽；非高峰不预留。

## 3. 调度规则（实现）

`lane_scheduler`（config.json）：

```json
{"enabled": true, "fast_lane": "http://127.0.0.1:8091", "slow_lane": "http://127.0.0.1:8092",
 "fast_models": ["qwen3.8-flash-fast","strata-a"], "pinned_models": ["strata-a","strata-b"],
 "reserve_by_hour": {"9":3,...}, "spread_when_idle": true}
```

规则（`schedule_lane()`）：

1. **快道请求**（`fast_models`）：在两条活着的 lane 里选**实时在途数更少**的那条；持平留在快道。
2. **普道请求**：
   - 普道还有空槽（`load < 4`）→ 普道；
   - 普道满了、快道够闲（`load_A < 4 − reserve`）→ 溢出快道；
   - 都不满足 → 留在普道排队（不在快道制造长队）。
3. **空闲分摊**（`spread_when_idle`）：普道已有人在跑、快道完全空闲、且快道还够预留 →
   把新请求分到快道，避免"一张卡忙、一张卡空转"。
4. **显式指定车道不参与均衡**：`strata-a` / `strata-b` 是调用方点名要的车道，保持死钉
   （只有该道真的连不上才改投）。
5. **保守兜底**：`/v1/status` 数据过期/缺失时视为"完全空闲"，宁可排到目标道也不凭空拒绝；
   一条道不可达时自动投另一条。

日志会打印每次决策，例如：

```
schedule: fast model=qwen3.8-flash-fast fast_load=1/4 slow_load=0/4 -> 普道
schedule: normal spill fast_load=0/4 slow 4>=4 reserve=3 -> 快道
schedule: normal spread fast_load=0 slow_load=1/4 -> 快道
```

## 4. 为什么这样能优化并发

1. **把两个 4 槽队列合成一个 8 槽池**：两条 lane 各自 batch 4，任何一条单独只能同时服务 4 条；
   调度按实时占用分配，第 5–8 条请求能立刻找到空槽，而不是在钉死的那条道上排队。
   上面实测 4 路 107.8 → 8 路 141.6 tok/s 就是这个容量池的体现。
2. **消除队头阻塞**：引擎 prefill 串行，一条 100k 的长 prompt 会把后面所有请求的 TTFT 拉长。
   调度器把新请求导向空闲道，长 prompt 只堵它自己那条道。
3. **保护快道语义**：快请求去"人少"的道（哪怕那是普道），高峰时段给快道留 1–3 个槽，
   普道溢出只能用剩余槽——快请求不会再排在普道批量任务后面。
4. **利用负载异质性**：普道以短请求为主、快道以长上下文/低延迟为主；分道后每道批窗口的行预算
   （8 行）更容易被同质请求填满，投机解码与专家缓存命中率更稳定。
5. **低负载时两张卡都用起来**：空闲分摊让第二条请求就落到另一张卡，而不是让一张卡吃满、
   另一张卡空转（用户明确要求）。

## 5. 已知限制与验证

- **粘性/前缀缓存**：调度会让同一会话偶尔换道，换道等于整段重读（TTFT 变差）。当前策略只在
  "目标道没有空槽"或"空闲分摊"时换道，正常负载下仍会稳定在一条道；后续可加"会话粘性优先，
  仅在目标道满时迁移"。
- **验证方法**：静默窗口下，8 路混合（4 快 + 4 普）分别测 `lane_scheduler.enabled=true/false`，
  比较聚合 tok/s、TTFT 分位和落道分布（`infer.db` 的 `lane_label`）。当前时段内部流量仍在，
  本轮 A/B 数据被真实请求污染，需重测。
- **回滚**：`lane_scheduler.enabled` 改 false 并重启 rag-proxy，即回到改动前的死钉行为
  （`pinned_models` 与其它逻辑不受影响）。
