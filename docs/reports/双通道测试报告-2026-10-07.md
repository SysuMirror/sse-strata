## 一、架构与本次变更

### 1.1 生产布局（双实例 + 钉核，方案2）

| 通道 | 模型 ID | 引擎 | GPU / CPU 核 | 监听 | 用途 |
|---|---|---|---|---|---|
| **快道** | `strata-a` | `strata-a`（独立引擎进程） | GPU0 / 核 0–15（NUMA0） | 127.0.0.1:8091 | 用户 agent 直连 |
| **普道** | `strata-b` | `strata-b`（独立引擎进程） | GPU1 / 核 38–53（NUMA1） | 127.0.0.1:8092 | 小任务/运维并发 |

- 每个引擎 = 完整模型（48 层全量）+ 各自 4 批槽（`--batch 4 --batch-mtp`）+ 13 个 CPU 专家池 worker；
- **钉核是性能命门**：两引擎必须 `taskset` 分核，否则 CPU 专家池互踩（实测每窗口 60ms 等 CPU，速度崩到 1/10）；
- 网关 `rag-proxy`（:8080，出口 23034）至此，**按模型 ID 分流**。

### 1.2 网关按模型 ID 分流（本次实现）

- `strata-a` → 8091（快道）；`strata-b` → 8092（普道）；
- 别名：`qwen3.8-flash`（外网现用名）→ 普道；`qwen3.8-flash-fast` → 快道；未登记模型 → 默认普道；
- `/v1/models` 列出全部 ID（带 `lane` 字段）；`/rag/status` 显示路由表；
- 路由器/中转处按模型 ID 放量与限流（快道限并发由中转处理，网关不做并发限制，两个 ID 都验证了 8 路）。

### 1.3 RAG 预处理修复（本次实现，用户要求"一次性灌入也要能检索"）

| 修复 | 内容 |
|---|---|
| 查询限长 | 巨型粘贴不再整条当查询（40 万 token 全送会打爆嵌入），取**头 1/4 + 尾 3/4**（问题通常在末尾）；`query_max_tokens=2048` |
| 嵌入预处理等待 | 超窗组装前等本会话所有块嵌入完成（**有界 120s、15s 无进度即放弃**）；只发生在"有缺失向量"时，**普通请求零影响** |
| 触发检测 | 内存字典（`sess.chunks`/`sess.vectors`/`EMB_CACHE`）实时比对，缺块才等——即"发现是一次性灌入（前面的没预处理）才并行向量化" |

**验证：预处理不影响正常请求**（实测）：45 万 token 灌入（602 块嵌入，等待 6.2s）期间，同引擎另一会话普通请求延迟 **0.84–4.03s**（首条 4s 是引擎 prefill 排队，非代理阻塞）。

### 1.4 内存化确认

- 代理全部 RAG 数据在内存：块/向量（实测 1162 块）、会话、组装块、重排缓存——**无磁盘写入**；
- 引擎侧停车快照/检查点在宿主内存；异步审计不受影响（不变）。

## 二、测试结果（全部经网关 :8080 / 出口，模型 ID 指定通道）

### 2.1 长上下文

| 测试 | 通道 | 结果 |
|---|---|---|
| 原生窗口 250k 单条针（deep 0.5） | A | ✅ 召回 YES · TTFT 79.3s · 解码 78.9 tok/s |
| 组装 350k（针在末尾最近窗口） | B | ✅ YES · TTFT 91.2s · 解码 50.3 |
| **一次性灌入 292k（70 轮，事实在第 1 轮）** | B | ✅ **YES** · 嵌入等待 6.6s · TTFT 102.7s |
| **一次性灌入 300k（事实在中部第 35 轮）** | B | ✅ **YES** · TTFT 86.9s |
| **一次性灌入 450k（60 轮）** | B | ✅ 完成 · TTFT 88.1s |
| 单条巨粘贴 300k **随机噪声**、问题埋在同一条消息内 | A | ❌ 已知边界（见 §三.2） |

### 2.2 8 路并发（两个 ID 都必须支持——已达标）

| 通道 | 完成率 | 聚合 tok/s | 每路解码 tok/s |
|---|---|---|---|
| `strata-a` 快道 | **8/8**（两轮重复） | 47.3 / 54.3 | 13.8–19.9 |
| `strata-b` 普道 | **8/8**（两轮重复） | 56.7 / 60.8 | 14.6–22.5 |

（引擎 4 批槽 + 门口排队不拒绝；TTFT 1.2–25s 为排队形态）

### 2.3 上下文 batch（4 路 × 16k 全新提示词）

| 场景 | 快道 A | 普道 B |
|---|---|---|
| 单通道 4×16k | TTFT 4.7 / 14.1 / 18.6s（间距 4.6s） | 4.9 / 14.6 / 19.3s（间距 4.8s） |
| **两通道同时 4×16k** | 5.0 / 9.7 / 14.3 / 18.8s（间距 4.6s） | 5.2 / 10.0 / 14.8 / 19.6s（间距 4.8s） |

→ **两条通道同时灌长文，排队形态完全不变：引擎、GPU、CPU 核全隔离。**

### 2.4 快道保护（双通道的核心价值）

| 场景 | 快道速度 |
|---|---|
| 快道独处 | 98–107 tok/s |
| **普道 4 路 × 16k 长文 prefill 风暴期间** | **94.8 tok/s · TTFT 2.1s** |
| 普道 3 路并发解码期间 | 119 tok/s |
| 对照：split 单引擎同负载 | ~37 tok/s |

### 2.5 资源水位

- 显存：每卡 ~23 GB（各自一份完整模型的 dense + 专家缓存）；
- 内存：176/216 GiB（两份专家 arena 47G×2 + PLE 页缓存 28.8G + 停车位 8G×2）；
- 双引擎同时加载 ~4–5 分钟（抢盘），错峰启动可缩短。

## 三、已知边界（诚实清单）

1. **单卡 prefill 慢于 split**：单卡 ~3.4k tok/s（split 双卡 6.7k）。16k ≈ 4.7s；250k ≈ 79s。长文档建议走 RAG 组装（组装后通常 100–220k）或接受 TTFT。后续如需要，可考虑"普道换回 split、快道独占一卡"的混合布局（一张 24G 卡跑大模型单卡 + 另一张跑快模型/或 split 需要两卡——需再评估）。
2. **单条巨粘贴 + 问题埋在同一条消息里**：随机噪声文档的检索无效（查询本身被噪声稀释；嵌入模型只吃 8192 token）。真实文档（自然文本）与多轮会话无此问题（上表已证）。
3. **组装块复用策略**：稳定块（前缀缓存友好）在一个会话内优先复用，可能与后续新问题不匹配；当前以缓存稳定为先，后续可按"查询变化幅度"做重建策略。
4. split 的纯聚合仍略优（4 路 149 vs 双实例 109）：双通道的价值在**隔离与快道保护**，不是聚合数字。
