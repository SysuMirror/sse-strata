## 2. 这次做了什么（怎么做的）

### 2.1 双卡 layer split 上线（上午）
把模型按 24/48 层切到两张 4090：`"gpu": [1,0]`、`--layer-split 24 --trim-stage-weights --batch-groups 2
--pool-workers 24`。专家常驻率 42% → **84%**（CUDA0 11549 + CUDA1 9030 槽），解码命中率 95–100%。
基线并发从 70.6/38.3/20.9（聚合 76.6/83.6）抬到 **96.5/77.0/118.1/131.3**。

### 2.2 引擎改动：批槽 MTP（"并发腰斩"的正面解法）

**问题**：批槽窗口每槽每窗口只出 1 个 token（无草稿），并发一上来每路速度就按份数摊薄。

**做法（全部在 `strata` 源码工作区，git diff 可见）**：
1. **链式窗口**（`src/core/verify.cpp` 等，上午）：一个窗口含 `S 槽 × L 行`（每槽 1 个携带 token + L-1 个
   MTP 草稿），一次验证，按槽各自接受/提交。逐 token 精确性验证（Stage A/B）通过。
2. **批量化 drafter**（`src/core/mtp.cpp` 的 `MtpDrafter::draft_batch` + `include/strata/core/mtp.hpp`，
   下午）：原实现对每个槽各跑一次单序列 drafter（S 次前向 + 每次一次主机往返）——这是链式第一版性能
   灾难的根因。现在把 S 个槽的整条链做成**一张捕获图**（键 `(S,L)`）：行→槽映射（`row_slots_`），
   K/V 写入与注意力逐行取各自槽的状态（与 verifier 批窗口同一套机制），**零内核改动**。
3. **崩溃根因与修复**（用户亲改 + 本次补强）：
   - 崩溃 = **链图懒捕获时 VRAM 不足**（生产 `--vram-reserve-mib 700` 时"加载完仅 416 MiB 空闲"，且提示
     路径借走 3.94 GiB 专家槽）→ 捕获失败 → `return 1` 静默退出（与 37 条"最后一行是链窗口捕获"的崩溃
     记录完全吻合；精确档测试全过是因为 `--pcie-frac 0` 不借那 3.9 GiB）。
   - 修复 a：**`chain_off` 降级**（用户）：链窗口/批链草稿任一失败 → 打印原因、永久关闭链、**引擎绝不退出**。
   - 修复 b：`--vram-reserve-mib 1600`（给捕获留头寸）。
   - 修复 c（本次，性能关键）：**不链的场景改走流水线 `pump`**——此前开 `--batch-mtp` 会绕过
     `--batch-groups 2` 的跨卡流水线，8 路因此掉 12%；现在采样槽回退 / `L<2` / `chain_off` 都走流水线，
     链窗口前先 `pipe_drain()`。**这一步是性能反转的关键**（4 路 97.6 → 148.9）。
4. 诊断工具（保留下次直接用）：`tools/crash_trace.c`（LD_PRELOAD：SIGSEGV/ABRT + **exit(1) 钩子**打调用栈）、
   `tools/chain_prod_repro.py`（生产档复现）、`~/bench/soak_chain.py`（生产形态浸泡）、
   `tools/strata-trace.sh`（调试包装）。

### 2.3 RAG 入口代理（上午上线 + 下午修性能）

* 结构：超窗检测（本地保守估算，只有接近窗口才精算）→ 会话分块（768 token/块，边界优先）→ 后台增量嵌入
  （内容哈希去重，bge-m3）→ 召回 top-200 → 重排 top-50 → 分数=0.55·重排+0.30·时近+0.15·角色 → MMR 去冗余 →
  贪心填满预算；**组装块在 TTL 内保持稳定复用**（这是"13 秒回答 250K 前缀"与"冷前缀一分钟"的分水岭）。
  全部内存、不落盘、缓存 ≤24h。
* **两个把速度拖慢的真 bug（用户反馈"单路只有 60 tok/s"的元凶）**：
  1. **流式转发攒包**：http.client 的 `read(8192)` 对 chunked 响应会攒满 8 KB 才返回（SSE 每事件 ~150B）
     → 每个流式响应白加 ~300ms 首包延迟，短回答 tok/s 直接腰斩。改用 `read1()` → 首包转发 407ms→**6ms**。
  2. **计数挤掉前缀缓存**：每请求前的 `count_tokens` 对引擎=插入"另一个对话"（对话停车默认关）→ 本会话
     前缀被挤出、随后整段重读（TTFT 0.1s→0.4s+）。改为短请求**跳过计数纯透传**。
  3. **超长会话的计数开销**（1M 测试中发现）：超窗后每轮都对整个 ~1M token 历史做精确计数（引擎 python
     分词，秒级）。修复：**前缀复用计数**——客户端逐轮追加是常态，上次请求的消息是新请求的前缀，只精算
     新增轮（+8 token 边界余量）；历史被改写时自动整段重算。每轮计数从秒级降到毫秒级。
* 修复后实测：**经代理与直连解码速率一致（126 vs 126 tok/s）、TTFT 相当**；引擎侧复用恢复
  （"30 reused + 7 read"）。A/B 脚本 `~/bench/single_ab.py`。

### 2.3b 晚场补丁：单条巨消息（1M 一次性粘贴）与质量收尾

1. **单条巨消息组装修复**（真实缺口）：`recent_window()` 原来对"单条消息就超预算"的输入整条保留 →
   该消息的块全被当成"最近窗口"排除 → 检索块拿不到候选 → 请求原样超窗 → **引擎 400 拒绝**
   （引擎从不截断超窗请求）。现在：单条超预算时**就地截断保留尾部**，被剪掉的前半段留在会话分块里供
   检索召回；并在"丢检索块"之后加了保险——仍超预算就从最长消息头部继续砍；计数超时/不可用时按
   1.5 字符/token **保守高估**（中文实际 ~1.7）。实测：**1,000,046 token 单条消息 → 144,363 token
   进引擎，两问两答正确**（首问 67s；次问 20s、前缀复用 144,356/144,363）。
2. **charset**：引擎与代理的响应头都补 `; charset=utf-8`（乱码根因：无 charset 时客户端按 Latin-1
   解 UTF-8）。
3. **会话完整性守卫**：会话键（system+首条 user 的哈希）撞车时立即重置检索状态，绝不串上下文
   （`test_session_isolation.py` PASS）。
4. 以上都写进了 `~/rag-proxy/README.md` §5b/§5c。

> 262144 以上（524288 / 1M）经 8080 走 RAG 组装：实测 1M 输入被组装成 ~151k token（最近窗口 +
> 检索块）再进引擎，所以这两行的 prefill 与 262k 档同量级。

**读数**：
1. **解码速度（"生成速度"本体）与上下文几乎无关**：单路全程 **107–141 tok/s**（1k→1M）；
   2 路时每路 **124–138 tok/s**（128k 及以上）。并发越高每路越低（行数预算被摊薄）。
2. **端到端速度被 TTFT 主导**：上下文越长、并发越高 TTFT 越大（prefill **独占**：并发长 prompt 排队）。
   1M/8 路时 TTFT 到分钟级——长上下文多用户的真实瓶颈（见 §5 建议）。
3. **聚合吞吐**：短上下文（1k）4–8 路 ~145 tok/s 是本机天花板；上下文越长聚合越低（prefill 排队吃掉时间槽）。

**经出口 vs 本地直连**：同时段 A/B（8k / 2 路）两者解码速率一致（差异在噪声内），出口不额外限速。
此前一次"出口只有 1.7–3.7 tok/s"的异常读数，根因是**引擎刚重启（冷缓存）+ 并发长 prompt 排队**，
且当时短答（30 token）把 prefill 摊进了平均。

## 3.8 MTP（投机解码）专项

**先说一个硬事实**：本引擎的 **serve 模式强制要求 MTP**——`strata` 二进制在 `--serve` 下若缺
`--spec T / --mtp DIR / --prefill CHUNK` 会直接 `exit 2`（源码 `src/program/generate.cpp:4180`）。
所以"关掉 MTP 跑基线"在生产形态下**不存在**：能对照的只有"**批槽是否用链式 MTP**"。

**A/B（同一脚本 `~/bench/mtp_ab.sh`、同样的 1K/8K 长回答负载、每点 1 轮，`runs/mtp-ab/`）**：

| 负载 | 链式批槽 MTP（现生产 `--batch-mtp`） | 批槽退回单 token 窗口（去掉 `--batch-mtp`） |
|---|---|---|
| 1K / 1 路 | 解码 **126.9** tok/s（聚合 81.8） | 解码 121.0（聚合 80.3） |
| 1K / 2 路 | 聚合 **71.9** | 聚合 61.5 |
| 1K / 4 路 | 聚合 134.6 | 聚合 **170.4** |
| 8K / 1 路 | 解码 **140.8** | 解码 130.1 |
| 8K / 2 路 | 聚合 **77.8** | 聚合 51.7 |
| 8K / 4 路 | 聚合 78.4 | 聚合 **90.4** |

**结论（诚实版）**：
* **1–2 路**：链式 MTP 更快（解码 +5~7%，聚合 +17~50%）；这符合机制——低并发时链窗口用
  "一窗 8 行验 4 个 token"替掉"一步 1 行"，把每步固定开销摊薄。
* **4 路**：本次单点采样显示**去掉链反而更快**（1K 170 vs 135、8K 90 vs 78）。这与今天上午
  `run.py` 口径（4 路 118→149 是链更好）**矛盾**，说明这里受样本波动影响大（同配置 2 路曾测到
  61.5 / 71.9 / 99.6 三个值）。**不据此改生产配置**；要定论需要每个配置多轮重复。
* **可执行的判断**：把"链窗口只用于 S ≤ 2、S ≥ 4 直接走跨卡流水线"当成一个候选优化
  （改 `chain_step` 一行），下次窗口用多轮采样验证。
* 生产保持 `--batch-mtp`（链式）：除了 1–2 路更好，它还带着今天做的 `chain_off` 自愈与
  流水线回退，是验证最充分的一档。

**草稿接受率（引擎明细日志 `parse_engine_log.py`，单路长回答 256 token）**：

| 上下文 | 1,000 | 8,000 | 32,000 | 128,000 | 262,144 | 524,288 | 1,000,000 |
|---|---|---|---|---|---|---|---|
| 接受率 | 50–53% | 59–62% | 65% | 59–66% | 64–68% | 58–69% | 60–85% |

**机制**（改动见 `~/docs/plans/ENGINE-BATCH-MTP-PLAN.md` §7–§9）：一个链窗口 = `S 槽 × L 行`
（`L = min(rows_per_slot, kVerifyMaxT/S)`，`kVerifyMaxT = 8`）；每槽 1 个携带 token + L-1 个 MTP 草稿，
一次验证，按槽各自接受/提交（`keeps[k]`）。单路时 L=8 → 一窗最多 8 个 token；4 路时 L=2；
8 路时 L=1（退化为单 token 窗口 → 走跨卡流水线）。接受率 ~60% 时可理解为
"8 行换 ~5 个 token"，也就是**约 1.6 行/token**；不链时是 1 行/token 但每步要多付一次固定开销
（主机往返 + 启动 + 跨卡同步），这就是低并发下链更快的来源。

## 4. 与目标的差距（诚实分析）

口径：**生成速度 = 解码 tok/s**（首 token 之后的稳定速率，引擎自报与客户端实测一致）；
端到端含 prefill，长上下文/高并发时被 TTFT 主导。

| 目标 | 实测（出口口径） | 判定与原因 |
|---|---|---|
| 单路 ≥120 | **121–141**（1k–8k；1M 档 117） | ✅ 达标 |
| 2 路 ≥120/路（聚合 240） | 每路 **56–60**（聚合 78–100） | ❌ 每卡需 120 tok/s；官方 4 卡 IQ3_S 实测聚合最好 360（=90/卡），本机 2 卡聚合天花板 ~145–170。**物理上不可达** |
| 4 路 ≥100/路（聚合 400） | 每路 **34–48**（聚合 78–145） | ❌ 同上；需要 3–4 张卡 |
| 8 路 ≥60/路（聚合 480） | 每路 **30–47**（聚合 76–145） | ❌ 同上；另受 `kVerifyMaxT=8` 行上限（8 槽时无草稿） |
| 上下文 ≥1M | 原生 262144 全窗口无损（NIAH 262k 3/3）；1M 经组装（NIAH 1M 3/3） | ✅ 机制达标；1M 的"逐字全窗口"受引擎 262144 限制，靠 RAG 组装，散落事实型任务（BABILong）命中率见文末 |
| 多模态 / 工具 / 流式 / 思考档 | 全通过（§3.3） | ✅ |
| 质量（不串上下文、不乱码、长上下文不失真） | 会话隔离 PASS、charset 修复、NIAH 9/9 | ✅（BABILong 1M 见文末） |
| 入口只开 8080 | ✅ | ✅ |

**为什么 2/4/8 路每路 120/100/60 达不到**：这三个目标换算成聚合是 240/400/480 tok/s。
本机（2×4090D、MoE 48 层、IQ3_XXS、QSA 稀疏注意力）实测聚合天花板 **145–170 tok/s**（短上下文），
而官方 4 卡 IQ3_S 的公开最好成绩是 360 聚合。也就是说"每卡 120 tok/s"已经**超过官方单卡水准**
（90 tok/s/卡），不是调参能补上的差距。

**要真正达标只有三条路**：① 加卡（3–4 张，聚合按卡数近线性放大）；② 换更小/更快的量化档
（Q2_0 已排除：质量不可接受）；③ 继续挤引擎（见 §5，但空间是 10–30% 量级，不是 2–5 倍）。

## 5. 后续建议（按性价比排序，含今晚新发现）

1. **prefill 批量化 / 非独占**（**今晚实测的最大痛点**）：现在长 prompt 的读入是独占且串行的——
   1M 档 8 路并发时 TTFT 达 4.7 分钟（8 × ~35s 排队）。把并发 prompt 的行合进一个批次、或让
   prefill 与其他槽的解码交错，能直接把"长上下文多用户"的体验拉起来。方向明确、收益大。
2. **高并发下少用链窗口**：今晚 A/B 显示 4 路时"去掉链、走跨卡流水线"反而更快（1K 170 vs 135）。
   建议把 `chain_step` 改成 **S ≤ 2 才链、S ≥ 4 直接 `one_group()`**，并用多轮采样确认（单点采样波动大）。
3. **检索块上限已放宽**（今晚已做）：`rerank_candidates` 50→200、MMR 选块 64→512，1M 输入的
   组装上下文从 ~65k 提到 ~218k token。
4. **`count_tokens` 超时/竞争**：长 prompt 单次 ~4.4s（20 万 token 以上可能超 10s），高并发时更慢 →
   退化为保守估算。可把计数改为引擎侧常驻前缀（或放到后台预计算），让窗口预算始终精确。
5. **解锁 `kVerifyMaxT > 8`**（MMVQ 模板 1..8 → 16、fused_gr/GMAX 联动、缓冲线性放大）：8 槽时也能带草稿，
   预计 8 路聚合 +20–40%。
6. **链窗口跨卡流水线**：当前链窗口不与其他组重叠，还有 10–20% 余量。
7. **对话停车打开**（`--conversation-cache-mib 8192`）：多会话交错时前缀复用更稳，TTFT 更可预测。
8. **P3 高速通道 B**（插队+专属槽，用户原选型）：等前几项完成后再做。

"散落事实"型任务上的水位就是这样。这是本机这台引擎的诚实边界，不是 bug。
