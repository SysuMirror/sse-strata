## 5. 今天改了四组东西

### 5.1 §5e 结构优先分块（09:46 改，10:25:54 上线）

* **为什么**：按长度硬切把一条"回合"（用户输入 → 工具调用 → 工具返回 → 回答）从中间劈开，检索带回无出处的碎片；
  实测三处硬伤——系统提示词整条丢失、最近窗口停在回合中间、巨型工具输出从行中间劈开。
* **怎么做**：`parse_turns()` 先解析回合 → 一个结构单元 = 一块、**块不跨回合** → 只有单条消息本身超预算才按 行→段→句 再切 →
  渲染时按原始先后并打回合标签 → `expand_context()` 按结构补全 → 系统提示词逐字保留在最前 → 最近窗口回合对齐。
* **实测**：A/B 对照（30 轮同一语料）系统提示词保留 ✅ vs ❌、行中碎片 0 vs 9、回合标签 17 vs 0（README §5e）。
* **顺带修掉的真问题**：组装块 TTL 内跨问题复用 → 提问阶段拿到灌入阶段的旧块（召回 0/6，旧实现 2/6）→
  由 `block_drift_rebuild`（重排器判覆盖度）兜住，实测 6/6 且**同话题追问仍复用**。
  为什么必须用重排器而不是嵌入余弦：句式相同的事实块余弦分不开（0.70 vs 0.48），重排器 0.80 vs 0.0004。
* **回滚**：`structure_chunking=false` / `block_drift_rebuild=false`（两个独立开关）。

### 5.2 §5f 窗口守卫（09:46 改，10:25:54 上线）

* **为什么**（生产翻车原文）：`400 prompt (231775 tokens) + max tokens (32000) exceeds the context (262144); requests are never truncated. Send a smaller max_tokens (at most 30361 here) (#545)`
  —— 网关当时记 `219021`、引擎数到 `231775`，差 **12,754（5.8%）**。**引擎从不截断**，所以算错一次就是一次客户端可见的失败。
* **怎么做**（三条通路全补）：① 估算改**上界**（CJK/数字 1.05、其他 0.70 tok/char，替代 `len/1.5`——它对数字串和单字重复 CJK 低估 1.5×）；
  ② **图片计入**（`image_tokens=1024`/张；实测 6 张 1024×768 差 **+4,602**）；③ 残差留余量 + 组装**必须收敛**；
  ④ 最后一道网：认引擎 400 里那句 `at most N here`，照它压 `max_tokens` **重发一次**。
* **实测**：离线 `test_window_guard.py` 40+ 断言全绿（今天 13:22 重跑 **ALL PASS 34s**，原始日志已留档）；
  真引擎验收见 §6.1。
* **回滚**：`retry_on_overfit=false`（关掉重试网）；估算上界要退需改代码。

### 5.3 §3.6 三项正确性修复（13:18–13:22 改，**13:47:15 上线**）

### 5.4 测试台修复（14:41）

跑 strata-a 时发现的**两个测试台 bug**（不是网关的问题，但会让验收结论失真）：

1. **构造器永远收敛不到目标**：`build()` 在"目标比当前 text 长"时执行 `text[:int(len(text)*target/n)]`——
   那是**向后切片**，Python 切不出更长的字符串 → 24 次迭代全空转，四档恒定停在目标之下 1.6%~3%
   （228159/231775、195567/200000）→ 两档"直连对照"根本没成立。**已修**（不够长就接一段，太长才按比例截断），现在四档误差 ≤ 0.01%。
2. **"网关那行账"取错行**：日志是**所有客户端共用**的，原来取"最后一行 ctx"会抓到别人的请求
   （实测抓到过一行 `提示词 359` 的陌生请求）。**已修**：只看本次请求之后新增的行，并优先挑 `（原始 X tok）` 与本档构造对得上的那条；
   找不到就打 `uncertain` 标记（第 4 档就是这种情况——它的账是 `ctx[透传(精确计数)]`，本来就不带"原始"）。
3. **补了不变量断言**：`引擎自己的 prompt + 送出去的 max_tokens + 8 ≤ 262144`。原来只断言"prompt 在窗口内"，没把输出预留算进去。

### 6.1 窗口守卫 · 真引擎验收（`--model strata-a --engine 127.0.0.1:8091`）

* **结论**：三档"引擎必然 400"的请求，经网关全部变成 200，且**每一档都满足** `引擎 prompt + 送出 max_tokens + 8 ≤ 262144`；

* 第 4 档的账：`ctx[透传(精确计数)]: 提示词 200102 + max_tokens 58396 … | ⚠ max_tokens 超余量已压到 58396`
  —— 客户端要 60,000，网关按"窗口−提示词−残差"压到 58,396 才发出去（= 262144−8−200102−3638）。
* 路由已核对：这批组装后的请求确实落在 **8091**（`strata-a.out.log`：`reading the prompt: 38,136 of 38,143 tokens`）。

### 6.2 思考预算守卫 · 生产实况

* **上线后立刻**（`rag-proxy.out.log` 13:47–13:48）：`思考预算 12288`（max_tokens 16384）、`思考预算 1366`（max_tokens 2048）
  —— 真实客户端流量已经在拿到预算；**带 `thinking` 的客户端请求不带该字段**（尊重客户端）。
* **strata-a 实况验证**（14:42:29）：一条 `max_tokens=2112`、无思考字段的请求 → HTTP 200 / `finish_reason=stop` / 回答"每人分 7/13 个苹果。"，
  账上是 `提示词 45 + max_tokens 2112 … 思考预算 1408`；而引擎**没有**记录收尾（基线 0 → 现在 0）——因为这次只想了 ~300 token。
  **这正是设计意图**：守卫是安全网，正常流量完全不受影响，只有"思考要吃掉几乎全部额度"时才收拢。
* **它什么时候真的会收尾**：真引擎预检里一条 harder 的请求触发了
  `[strata] thinking budget reached (1408 tokens): wrapping up the thinking`（`strata-b.out.log`，此前该文件 0 次）。

### 6.3 顺带查出的两件事（都不是故障，但值得记）

1. **单条巨消息会被塌缩成尾部 ~38k**：四档构造 231,810 / 250,016 / 261,020 tok 的**单条**消息，组装后进引擎的都是
   `38,143 / 38,153 / 38,152` tok，且账上是 `最近窗口 65521 + 检索块 0`。
   原因：单条消息超预算时 `recent_window()` 保留尾部 `max(1024, 预算 × chars_per_token)` 个**字符** = 65,536×2.5 = 163,840 字符；
   英文散文实测 4.30 字符/token → 163,840 字符 ≈ **38,100 token**。**后果**：一次性粘 23 万 token 的文档，模型实际只看到尾部约 16% 的内容，
   而 `检索块 0` 说明**被剪掉的前半段没有被检索回来**（排除是按**回合**做的，这一回合整个在窗口里 → 它的块全部被排除）。
   → 这与 `README.md` §5c 第 4 条"被剪掉的前半段留在会话分块里供检索召回"**不一致**；列入 §9 待定。
2. **最近窗口对英文少用约 42% 的预算**：窗口裁剪用的是估算口径 `chars_per_token=2.5`，而英文实测 4.30 字符/token
   → 65,536 的预算只用到 ~38.1k（58%）。CJK 语料下这个估算反而是准的。这是**保守**方向的偏差（不会超窗），但白白少了窗口。
3. （供对照）今天 13:03 那次"看起来被截断"：**不是截断**——转录 `stop_reason=end_turn`、`out 2113`（含 5,624 字符 thinking + 14 字文本），
   引擎 `done: 2113 (stop)`，网关全程透传、`overfit_* = 0`。是模型自己说了"Let me write."却没发出工具调用。完整证据链见技术文档 §6。

## 8. 已知限制与风险（合并 `README.md` §7 与技术文档 §8）

**结构性的（设计如此）**

1. **全内存、无持久化**：重启（含 pod 重建）即清空嵌入/重排/组装/会话缓存——今天 13:47 的重启就清了一次。
2. **跨会话不共享缓存**：嵌入缓存全局、但检索按会话索引，跨会话不互相召回。
3. **图片不嵌入内容**：只记占位符；今天只保证"token 账算得对"（`image_tokens=1024`/张）。
4. **鉴权由客户端自带 key**：网关严格透传，**从不替客户端补 key**（补 key 等于绕过引擎鉴权）；
   `~/logs/strata-api-key.txt` 只用于网关自身的 `count_tokens` 与测试脚本直连引擎对照。
5. **`:8081` 与 `:8080` 一样对 pod 外可访问**；要对外提供需再套一层鉴权。

**精度天花板（改动前基线，改动后未重测）**

6. **1M 本质是检索精度**：清晰单针事实任意深度接近 100%（NIAH 15/15、外网 3/3）；
   **多条相似事实散落召回是真实短板**（BABILong 2/15、生产形态 3/7），失败模式含**自信地答错**（`pod@40→COBALT-3141`、`harbor@150→MEADOW-2718`）。
7. **`rag_1m_test.py` 的 1M 是名义 1M**（`tok_per_turn × 1.5` 在中文下 ≈ 2,500 tok/轮，300 轮 ≈ 750k）；引用 token 数要用网关 `ctx[...]` 的真实值。
8. **`/metrics` 的 `requests[0]` 不能用来断言单次请求**（它是引擎"最近一条"，混着别的会话和网关自己的 count_tokens）；
   真引擎验收必须读响应自带的 `usage`——`G.log` 的教训，今天的测试台已按这个改。

**今天新增的两条**（§6.3）

9. **单条巨消息塌缩到尾部**（可检索性缺口）。
10. **最近窗口对英文只用到 ~58% 预算**（估算口径 `chars_per_token=2.5` 对英文偏保守）。

**并发（技术文档 §5.3）**

11. R1–R4 已修并上线；**R5（`COUNTERS` 非原子自增，仅观测少记）未修**；R3 缺专门的并发用例。
12. 客户端断开后网关仍会把活干完（有界等待最长 `embed_wait_s=120`）→ `err.log` 里的 BrokenPipe traceback（历史 93 次）。
