## 1. 它解决什么

模型窗口 262144。对话/资料超过窗口时，本代理把"更早的历史"换成**检索出来的片段**，
让上下文始终 ≤ 窗口；短对话原样透传（行为与直连 :8080 完全一致）。
上限：会话历史可远超 256K（检索库有多大就能有多大），检索/组装全程在内存。

## 2. 架构

```
客户端 ──► :8080 rag_proxy.py ──► 127.0.0.1:8090 引擎（原文或改写后的 messages）
                  │
                  ├─ 分块（消息边界优先，768 tok/块，128 重叠）
                  ├─ 嵌入队列（后台线程）──► bge-m3 @ 10.42.0.233:8080/v1/embeddings
                  ├─ 检索（余弦 top-200）──► bge-reranker-v2-m3 @ 10.42.0.71:8080/v1/rerank
                  ├─ 组装（预算内：系统+检索块+最近窗口），组装块 TTL 内**稳定复用**（前缀缓存友好）
                  └─ 内存缓存：嵌入（内容哈希，永久）/ 重排（TTL 3h）/ 组装（TTL 3h）/ 会话（TTL 24h）
```

## 5. 关键行为

1. **触发**：`count_tokens(messages) > 262144 - 8 - max_tokens`（max_tokens 预留上限 32768）。计数走本机
   `/v1/messages/count_tokens`（不跑模型）；失败退化为 chars/2.5 估算。
2. **预算**：组装后仍会**精确复核**一次；超了就按 0.7 比例砍检索块，最多三次，仍超则丢块（退化到最近窗口）。
3. **最近逐字窗口**：默认 65536 token，逐字保留（不动）。
4. **检索块**：向量召回 top-200 → 重排 top-50 → `0.55*重排 + 0.30*时近(指数衰减) + 0.15*角色权重`
   → **MMR（λ=0.7，用块向量算相似度）去冗余** → 按分数贪心填充预算。
5. **前缀缓存友好**：检索块在 TTL（3h）内**复用它，不重排**；只有 ① TTL 到期、② 最近窗口吃满预算
   （compaction）才重建。这是 TTFT 0.8s 与 60s 的分水岭（引擎实测前缀复用 17×）。
6. **嵌入**：内容哈希去重（重复的工具输出/重复段落只嵌一次），后台批量嵌入，请求路径**只等查询向量**
   （上限 5s，超时降级）；每轮新内容到达就入队，所以掉出窗口前早已就绪。
7. **降级**：嵌入/重排不可达 → 组装只保留最近窗口（照常 200）；代理自身异常 → 原样透传。
   计数器 `degraded` 记录。

## 5b. 性能修复（2026-10-06，重要）

1. **流式转发改用 `r.read1(8192)`**：http.client 的 `read(n)` 对 chunked 响应会攒满 n 字节才返回——SSE 每事件
   ~150B，等于给每个流式响应加 ~300ms+ 首包延迟（短回答的 tok/s 直接腰斩）。`read1` 有数据即回
   （实测首包转发 407ms → 6ms）。
2. **短请求跳过 `count_tokens`**：精确计数对引擎而言是"另一次请求"（对话停车默认关闭），会把本会话的
   前缀状态挤出 → 随后生成整段重读（TTFT 0.1s→0.4s+）。现在先用本地保守估算（1.5 字符/token，×2 余量）
   判断"远低于窗口"就纯透传；只有接近/超过窗口才精确计数。
   修复后实测：经代理与直连解码速率一致（126 vs 126 tok/s）、TTFT 相当；引擎侧前缀复用恢复
   （`30 reused + 7 read`）。A/B 脚本：`~/bench/single_ab.py`。

## 5c. 质量补丁（2026-10-06 晚）

1. **charset 修复（乱码根因）**：响应头原来只写 `application/json`、`text/event-stream`，没有 charset。
   部分客户端（含浏览器 fetch / 部分 SDK）在没有 charset 时按 Latin-1 解码 UTF-8 字节 → 中文乱码。
   现在代理与引擎两处都补 `; charset=utf-8`（流式与非流式都补）。
2. **会话完整性守卫（防串上下文）**：会话键 = hash(system + 首条 user)，模板化客户端（同一套提示词、
   同样开场白）会**撞键**。现在每次请求先比对本次消息序列与该会话已见历史：公共前缀比
   "允许最后一轮不同"更短 → 立即 `sess.reset()`（日志 `session reset: history diverged at message k`），
   绝不拿别的会话的块来做检索。测试：`test_session_isolation.py`（两段同头不同内容的对话，
   小窗口触发组装；B 段问"保险箱密码"必须答 UNKNOWN，出现 A 段埋的 ALPHA-111 即失败）——**PASS**。
3. **计数前缀复用（超长会话）**：超窗后每轮都对整个 ~1M token 历史做精确计数（秒级）。客户端逐轮追加是
   常态，上次请求的 messages 就是本次的前缀 → 只精算新增轮（+8 token 边界余量）；历史被改写/截断时
   自动整段重算。每轮计数从秒级降到毫秒级。
4. **单条巨消息（1M 一次性粘贴）的组装修复**：`recent_window()` 原来对"单条消息就超预算"的情况整条保留
   → 组装完全失效：检索块拿不到候选（该消息的块被当成"最近窗口"排除），请求原样超窗 → 引擎
   **400 拒绝**（引擎从不截断）。现在：单条超预算时**就地截断保留尾部**，被剪掉的前半段留在会话分块里
   供检索召回；并在丢块之后加了一道"仍超预算就从最长消息头部继续砍"的保险（估算口径按 1.5 字符/token
   保守高估，计数超时也能收敛）。实测：1,000,046 token 单条消息 → 组装成 144,363 token 进引擎，
   两问两答正确（首问 67s，次问 20s、前缀复用 144,356/144,363）。
5. **窗口算术与 max_tokens 自动压缩（2026-10-07，Claude Code 报 400 之后加）**：引擎对
   `提示词 + max_tokens + 8 > 262144` 的请求**直接 400、从不截断**，所以网关必须自己保证装得下：
   * **计数带上 `tools`/`system`**：原来只数 `messages`，漏掉工具定义（Claude Code 光工具就有上万
     token）→ 以为装得下 → 透传 → 引擎 400（生产实例：237,795 + 32,000）。
   * **组装后的尺寸用精确计数**（原来用估算 chars/2.5，中文偏低 ~40%，按它压 max_tokens 仍会超窗）。
   * **max_tokens 自动压缩**：`clamp_max_tokens()` 把客户端要的输出压到 `窗口 - 8 - 提示词` 余量。
   * **每请求一行窗口算术日志**（`grep 'ctx\['`）：
     `ctx[组装]: 窗口 262144 = 提示词 55772（原始 990666 tok） + max_tokens 64 + 边界 8 | 余量 206364 最近窗口 65544 + 检索块 29102`
   * 实测边界：200K+max 200000（压缩后通过）、240K+max 32000（组装通过）、225K+tools+max 32000（组装通过）。
6. **已知行为（不是 bug，写下来免得误判）**：引擎繁忙时 `/v1/messages/count_tokens` 可能排到 10s 超时
   （长 prompt 单次约 4.4s，8 路并发时更长）→ 代理退化为 chars/1.5 估算。该估算对中文**高估**约 15%
   （真实 ~1.7 字符/token），后果只是"组装更保守一点"，不影响正确性。

## 5e. 分块重写：结构优先（2026-10-08）

**动机**：1M 精度报告 §1 里写的"其余内容切成 768 token 的块"是按**长度**切的。长度切分把对话
的语义单位（一条回合 = 用户输入 → agent 工具调用 → 工具返回 → agent 回答）从中间劈开，检索带回的
就是没有出处的碎片——报告 §2.6 的"张冠李戴"（把更近的相似事实搬过来）正是这个后果之一。实测的三处硬伤：

1. **系统提示词会丢**：`recent_window()` 跳过 `role=system` 的消息，而组装只补 Anthropic 的
   `body["system"]`——OpenAI 形态（system 在 messages 里）一旦触发组装，系统提示词**整条消失**。
2. **最近窗口停在回合中间**：实测窗口里只剩一条孤零零的工具返回，产生它的工具调用和它回答的问题
   都在窗口外。
3. **巨型工具输出从行中间劈开**：旧切法实测把 `…retry=2\nline 27…` 切成下一块的 `y stage 1 reported…`。

**新做法**（`rag_proxy.py` 的"结构解析/分块"一节）：

* **先解析回合**：`parse_turns()` 把 messages 解析成回合，消息按结构归类
  （`user` / `assistant` / `tool_call` / `tool_result` / `system`）。Anthropic 把工具返回放在 user
  消息里，这里识别成 `tool_result` 而**不是**新回合——否则每个工具返回都会被当成一轮新问题。
* **一个结构单元 = 一块**，块绝不跨回合；只有单条消息本身超 `chunk_tokens` 才按
  **行 → 段落 → 句子 → 硬切** 的自然边界再切（重叠也只带整行/整句，不再回退 128 个字符）。
  日志/代码/表格类工具输出走"整行装箱"，绝不切行。
* **块标识恒定 → 嵌入直接复用**：块边界只由本条消息自己的结构决定，与邻居长度无关。实测 40 轮
  真实 agent 会话逐条到达：逐单元成块是**零重嵌**（每条消息只嵌一次、无陈旧块）；而"合并相邻单元
  成块"要白做 100 次嵌入、留下 100 个陈旧块在检索索引里当噪声（`test_chunking.py` §7 固化了这个对照，
  这也是为什么不合并）。
* **语序在渲染时还原**：`render_block()` 按**原始先后**输出检索块，每换一条回合打一行结构标签
  （`--- turn 27 · user → assistant(tool_call: lookup) → tool_result → assistant`）；
  `expand_context()` 做**结构补全**——选中的块若属于某条回合，预算够就补齐整条回合（工具返回带上
  产生它的工具调用、回答带上它回答的那个问题），预算不够至少带回同消息其余分段与回合锚点。
  切分负责稳定，渲染负责语序。
* **系统提示词逐字保留在最前**：两种形态都顾到（`body["system"]` 与 messages 里的 `role=system`）。
* **最近窗口回合对齐**：窗口边界一定落在回合边界上，要么整回合在窗口里、要么整回合交给检索；
  单回合超预算时**先保回合骨架**（短单元整条留下，巨型输出按行截尾），旧版是从头部整条丢——
  结果常常把用户问题丢了、只留一坨巨型工具输出。
* **复核超预算时按整块砍**（砍优先级最低的整块），不再把块文本按 0.7 比例从中间截一刀。

**新配置**：`structure_chunking`（false=退回旧的分块，A/B 用）、`context_expand_ratio`（检索块预算里
留给结构补全的比例，默认 0.25）。

**测试**：

  补全/旧行为回退），**全过**。
* `test_structure_e2e.py` + `mock_upstream.py`——端到端 A/B：同一份 agent 形态语料（30 轮，6 条事实

**顺带查出的一个真问题（尚未改，需要决策）**：组装块在 TTL（3h）内**跨问题复用**，而 TTL 判定
只看时间与"窗口是否吃满"，**不看问题变没变**。于是提问阶段拿到的还是灌入阶段为别的查询建好的旧块。
同一份语料把 TTL 设成 3h 再跑：新实现召回 **0/6**、旧实现 **2/6**（TTL=0 时两者都 6/6）。
这很可能就是报告 §2.6 生产形态 300 轮 **3/7** 的主要成因——那 7 个问题问在灌入之后，拿到的正是
灌入阶段的旧组装块。

已修：判据开关 `block_drift_rebuild`（**默认开**）。判据不是"新问题跟旧问题像不像"，而是用**重排器**
问一句"**当前块里有没有真能回答这个问题的内容**"——块内优先级最高的 ≤128 块（每块截 600 字符）对新
问题重排，分数最高那块都答不上（`block_relevance_min=0.30`）就重建。

**为什么必须用重排器而不是嵌入余弦**（试错过，记下来免得再走一遍）：
* 判据若用嵌入余弦比"全历史最好的块 vs 块内最好的块"，**句式相同的事实块它分不开**：
  实测 `the pod code is …` 0.70 vs `the vault code is …` 0.48，块里塞满填充后差距更小 →
  阈值几乎永不越过，23 次组装只触发 1 次重建，召回只有 **2/6**。
* 重排器是交叉编码器，同一组文档实测 **0.80 vs 0.0004**（差四个数量级）。判据换成分据后立刻 6/6。

实测（同一份语料 30 轮 / 窗口 16384 / 最近窗口 4096 / TTL=3h 生产语义）：

| 组装块策略 | 召回 | 判据触发的重建 | 已覆盖的追问 |
|---|---|---|---|
| TTL 内无脑复用（改动前行为） | 0/6 | — | 复用 |
| 每问都重建（TTL=0） | 6/6 | 每次都重建（前缀缓存全丢） | 重建 |
| **覆盖度判据（现在的默认）** | **6/6** | **6 次**（正好一问一次） | **仍复用**（0 次额外重建） |

对照的旧实现（改动前的备份）在同样 TTL 语义下只有 **2/6**。

**代价说清楚**：每个超窗请求多一次重排调用（≤128 块 × 600 字符，实测每个问题整轮 ~2s）；
只有"块确实没覆盖这个问题"时才付重建的钱（= 引擎前缀缓存失效，TTFT 秒级→分钟级）。
同话题连续追问照旧复用，前缀缓存不受影响。可调：`block_relevance_min`（判据阈值）、
`block_check_docs` / `block_check_chars`（判据便宜程度）、关掉开关即回到旧行为。
观测：`/health` 的 `counters.block_rebuilds`。

## 5f. 窗口守卫：不再把必然 400 的请求放出去（2026-10-08）

翻车现场（生产 :8080 → strata-a，Claude Code 会话）：

```
API Error: 400 prompt (231775 tokens) + max tokens (32000) exceeds the context (262144);
requests are never truncated. Send a smaller max_tokens (at most 30361 here) … (#545)
```

网关日志当时记的是 `ctx[组装]: 窗口 262144 = 提示词 219021（原始 316363 tok） + max_tokens 32000 + 边界 8 | 余量 43115`
——**网关以为还剩 43k，引擎自己数到 231,775，只剩 30,361**。差 12,754 token（5.8%）。引擎对超窗请求
**直接 400、从不截断**，所以这道算术错一次就是一次客户端可见的失败。三条真实通路，全部补上：

**① 旧估算不是上界，而快通道拿 ×2 替它兜底。** 旧公式 `len/1.5`，判据 `est*2 < budget`。对真引擎
`count_tokens` 标定后（`/tmp/ragdev/calib.py`、`probe_est.py`，只调计数接口、不跑模型）：

| 文本类别 | 实测 tok/char | 旧 est(tok/char) | 旧 est 相对真实 |
|---|---|---|---|
| 英文散文 | 0.188 | 0.667 | 高估 3.5× |
| 工具 JSON | 0.266 | 0.667 | 高估 2.5× |
| 代码 | 0.389 | 0.667 | 高估 1.7× |
| 随机词 | 0.474 | 0.667 | 高估 1.4× |
| 中文散文 | 0.506 | 0.667 | 高估 1.3× |
| 中英混排 | 0.625 | 0.667 | ≈持平 |
| **数字串** | **1.000** | 0.667 | **低估 1.5×** |
| **单字重复 CJK** | **1.000** | 0.667 | **低估 1.5×** |

现在按字符分类取**上界**（`tok_per_char_cjk=1.05`、`tok_per_char_digit=1.05`、`tok_per_char_other=0.70`，
都高于实测最坏那一档），再加每消息模板开销（实测模板固定 ~45 + 每消息 ~6.7 → 取 8）。快通道判据
因此从 `est*2 < budget` 改成 `est + 残差 ≤ budget`：**估算本身安全，就不需要那个 ×2 的运气**。

**② 图片谁都没算。** `/v1/messages/count_tokens` 把一张图只数 1 个 pad，而引擎 `prepare()` 把它展开成
每图一个 token（实测 `probe_img.py`，同一份 body 两边对比、生成侧读 `/metrics` 的 `prompt_tokens`）：

| 请求 | count_tokens | 引擎 prepare | 差额 |
|---|---|---|---|
| 1 张 64×64 | 66 | 74 | +8 |
| 1 张 512×384 | 66 | 358 | +292 |
| 1 张 1024×768 | 66 | 297 | +231 |
| **6 张 1024×768** | 161 | 4763 | **+4602** |

（纯文本请求两边**逐 token 完全一致**，实测 gap 0 —— 差额只在图片上，见 `probe_gap.py`。）
现在 `image_tokens=1024` 每张，估算与精确计数两条路都算进去。

**③ 残差没留、砍无可砍就作罢。** `clamp_max_tokens` 以前按 `窗口 - 边界 - 提示词` 算余量，一点残差都不留；
组装的最后一段砍到"最长消息不足 4096 字符"就 break，然后照发。现在：余量再减 `clamp_margin_tokens(512) +
prompt/64`；组装的收敛循环改成"砍最长消息头部 → 不够就丢最近窗口里最旧的整条消息"，**必须收敛到装得下**；
RAG 逻辑自己出错时的降级透传也不再原样转发，先按上界估算压一次 max_tokens（`_guard_body`）。

**最后一道网（与上面三条独立，兜住没想到的差额）**：引擎的 400 原话里已经写了"这里最多还能给多少
max_tokens"。`_proxy` 现在认这句话——按引擎报的余量压小 max_tokens **重发一次**，客户端拿到的是正常
回答而不是 400。计数器 `overfit_retries` / `overfit_failures`（后者 = 提示词本身就超窗，压输出救不了）。

回归测试：`test_window_guard.py`（**40+ 断言全绿，35s**）
* **A 组 离线单元**：上界对 8 类实测 tok/char 逐一成立（并断言旧公式在数字串/单字重复 CJK 上确实低估）；
  图片块识别（Anthropic 与 OpenAI 两种形态）；clamp 用生产那组数字（231775 + 32000 → 压到 26228，
  比引擎报的 30361 更保守）；`overfit_room`/`patch_max_tokens` 解析引擎原话；降级透传也压 max_tokens；
  **组装收敛**——把 `count_tokens` 换成"比上界还多算 30% 且随砍随降"的假引擎，逼出两条收敛手段
  （有巨型消息 → 从头部砍最长消息；全是小消息 → 丢最近窗口里最旧的整条消息），两种都必须收敛到装得下。
* **B 组 端到端**：`mock_upstream.py --window` 开成严格窗口模式（超窗照 #545 原话报 400，图片按 800 tok 展开
  而 `count_tokens` 只数 1 个），跑真 `rag_proxy.py`：6 档尺寸扫描客户端零 400、每条进引擎的请求都装得下、
  10 张图的请求不超窗、日志带"计数残差"。
* **B3 重试网**：mock 一次性谎报"我数到的比你多 1500"，网关照引擎报的余量把 max_tokens 压小重发一次
  → 客户端 200、`overfit_retries=1`、`overfit_failures=0`。
* **C 组 降级**：嵌入/重排指到 127.0.0.1:9（立刻拒绝）→ 超窗请求仍 200，进引擎的请求仍装得下。

真引擎验收（不是判据算术，而是"引擎自己数到多少"）：`~/bench/window_guard_live.py --model strata-b`
——用原生 tokenizer 精确构造 231,775 / 250,000 / 261,000 / 200,000 tok 四档提示词，同一份 body 先走
网关（期望 200）再**直连引擎**（期望 400，对照组），每次请求后读引擎 `/metrics` 的 `prompt_tokens`
断言 `引擎口径 prompt + 8 <= 262144`。

## 5d. 双通道路由 + 一次性灌入预处理（2026-10-07）

* **模型 ID 分流**：`config.json` 的 `model_routes`——`strata-a`→8091（快道）、`strata-b`→8092（普道）；
  未登记模型走 `default_upstream`（普道）。`/v1/models` 列出全部 ID（带 `lane` 字段）；中转按 ID 限流。
* **查询限长**（`query_max_tokens=2048`）：巨型粘贴不再整条当查询（40 万 token 全送会打爆嵌入队列），
  取**头 1/4 + 尾 3/4**（问题通常在末尾）——修复前"问题埋在巨消息里"的检索全空。
* **嵌入预处理等待**（`embed_wait_s=120`）：组装前若本会话有块未嵌入（一次性灌入的典型情形），
  在请求线程里等它嵌入完（15s 无进度即放弃）——TTFT 付一次预处理代价（实测 600 块 ~6s），
  **不再静默退化成"零检索块"**。触发检测就是内存字典比对（`sess.chunks` vs `sess.vectors`），
  向量齐的请求零等待；普通（不超窗）请求根本不走这段路径，**不受影响**（实测：灌入期间普通请求 0.84–4.03s）。

## 5g. 上游 failover（2026-10-21）

引擎换版本必须重启，而冷启动要 **6–10 分钟**（专家 arena 40 GiB 从盘重建）。这段时间里，
被 `model_routes` 钉到那条 lane 的模型（`qwen3.8-flash-fast` → 8091、`qwen3.8-flash` → 8092）
以前会直接收到 `502 rag proxy: upstream failed: ConnectionRefusedError`，对外就是"网站挂了"。

现在 `_proxy()` 里加了一条保底路径：

```
except urllib.error.URLError:
    若 sent == False（还没给客户端写过响应头）
      alt = failover_upstream(当前上游)      # upstreams() 里另一条，TCP connect 探活，2 秒缓存
      有 → 计数 upstream_failover +1、日志「改投 Y」、递归重试一次（failover=False 防循环）
      没有 → 仍然 502
```

- **只在连接阶段失败**时生效；已经写出响应头之后的中断（读流中途断开）无法改投，仍按原样断开。
- 实测：隔离实例（`:8099`，上游指向死端口 `:9`）→ 自动改投 8091 并正常返回；
  2026-10-21 切 B 的窗口里，`qwen3.8-flash` 请求日志出现 `改投 http://127.0.0.1:8091`、**1.16 s 返回**。
- 它是**兜底**，不是零停机方案：改投过去的那条 lane 也要扛额外负载，滚动切换仍是正确做法。

## 7. 已知限制 / 后续

* 鉴权：客户端需自带引擎 API key（代理只透传，不再替无 key 请求带 key）——升级注意。
* 全内存、无持久化：代理重启（含 pod 重建）后缓存清空，会话需重新"渐进"一轮。
* 跨会话不共享缓存（嵌入按会话索引；`EMB_CACHE` 全局但未做跨会话检索）。
* 图片只记占位符（不嵌入图像内容）；超长单条消息按段落硬切，可能截断语义。
* 漂移检测简化：只按 TTL 与"窗口吃满"重建，未做话题漂移判定（可加：查询向量与块查询向量的余弦）。
* 端口 8081 对 pod 外可访问（同 8080 一样对外）；若要对外提供，建议在网关侧再套一层鉴权
  （代理目前不校验客户端 key，只向上游转发）。

## 8. 交接要点

* 所有可调项在 `config.json`，改动后 `supervisorctl restart rag-proxy` 生效。
* 想加"话题漂移重建"：`assemble()` 里 `fresh` 判定处加查询向量与 `sess.stable_block_query` 的余弦阈值即可。
* 想加"跨会话缓存"：`build_memory_block()` 里把 `cosine_matrix(sess, qv)` 换成全局块索引。
* 与引擎的关系：完全不碰引擎/服务端；引擎升级、重启都不影响本代理——
  被路由到的那条 lane 不可达时会**自动改投另一条**（§5g，2026-10-21 起；之前是透明 502）。
