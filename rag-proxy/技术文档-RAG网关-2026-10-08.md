### 2.3 `:8080` 到底做什么

三种归宿，每次请求都会在 `~/deploy/logs/rag-proxy.out.log` 留一行（`grep 'ctx\['`）：

1. **快通道透传**：上界估算就装得下 → 连 `count_tokens` 都不调，原文转发（这是 99% 的请求）。
2. **精确计数透传**：估算不够放心 → 走 `/v1/messages/count_tokens`（带 `tools`/`system`），仍装得下就透传，必要时压 `max_tokens`。
3. **组装**：装不下 → 检索 + 组装成 ≤ 窗口的 messages 再发。

### 3.1 §5b 性能修复（2026-10-06）

* **动机**：`http.client` 的 `read(n)` 对 chunked 响应会攒满 n 字节才返回——SSE 每事件 ~150B，等于给每个流式响应加 ~300ms+ 首包延迟（短回答 tok/s 直接腰斩）〔README §5b〕。
* **做法**：流式转发改用 `r.read1(8192)`（有数据即回，逐事件转发）〔`rag_proxy.py:1277-1291`〕；短请求先用本地保守估算判断"远低于窗口"就纯透传，避免 `count_tokens` 把本会话前缀状态挤出〔`rag_proxy.py:1403-1417` 注释〕。
* **实测对照**：首包转发 **407ms → 6ms**；经代理与直连解码速率一致（**126 vs 126 tok/s**）、TTFT 相当；引擎侧前缀复用恢复（`30 reused + 7 read`）。A/B 脚本 `~/bench/single_ab.py`〔README §5b〕。
* **配置项**：无新增（行为写死在代码里）。
* **回滚**：把 `read1` 换回 `read`（会退回高延迟）。

### 3.4 §5e 结构优先分块重写（2026-10-08）★本轮改动

* **动机（实测三处硬伤）**〔README §5e〕：
  1. **系统提示词会丢**：`recent_window()` 跳过 `role=system`，而组装只补 Anthropic 的 `body["system"]` → OpenAI 形态（system 在 messages 里）一旦触发组装，系统提示词**整条消失**。
  2. **最近窗口停在回合中间**：窗口里只剩一条孤零零的工具返回，产生它的工具调用和它回答的问题都在窗口外。
  3. **巨型工具输出从行中间劈开**：旧切法实测把 `…retry=2\nline 27…` 切成下一块的 `y stage 1 reported…`。
* **做法**（`rag_proxy.py` 的"结构解析/分块"一节，`384-608`）：
  * `classify()`/`parse_turns()` 把 messages 解析成**回合**；Anthropic 把工具返回放在 user 消息里，这里识别成 `tool_result` 而**不是**新回合〔`384-469`〕。
  * **一个结构单元 = 一块**，块绝不跨回合；只有单条消息本身超 `chunk_tokens` 才按 **行 → 段落 → 句子 → 硬切**〔`498-526`、`558-579`〕。
  * 块标识只看本条消息自己的结构（`sha1(role\x00text)`）→ 逐轮追加历史时**零重嵌**〔`540-555`〕。
  * 渲染时按**原始先后**输出并打回合结构标签；`expand_context()` 做**结构补全**（补齐整条回合 / 同消息分段 / 回合锚点）〔`897-963`〕。
  * 系统提示词逐字保留在最前（两种形态都顾到）〔`1086-1093`、`1143-1148`〕；最近窗口**回合对齐**，单回合超预算时**先保回合骨架**〔`850-884`〕；复核超预算时**按整块砍**〔`1165-1182`〕。
* **实测对照**（`test_structure_e2e.py` + `mock_upstream.py`，mock 只在事实真的进窗时才答对，所以召回率纯粹反映网关质量；30 轮 / 窗口 16384 / 最近窗口 4096）〔README §5e〕：

  | | 新（结构优先） | 旧（按长度） |
  |---|---|---|
  | 召回 | 6/6 | 6/6 |
  | 系统提示词保留 | ✅ | ❌ 丢了 |
  | 行中间劈开的碎片 | 0 | 9 |
  | 检索块回合结构标签 | 17 处 | 0 |
  | 事实块带回回合锚点 | ✅ | ❌ |

* **顺带查出并已修的真问题**：组装块在 TTL 内**跨问题复用**，判据原来只看时间与"窗口是否吃满"，于是提问阶段拿到灌入阶段为别的查询建好的旧块。同一份语料 TTL=3h：新实现召回 **0/6**、旧实现 **2/6**（TTL=0 时两者都 6/6）——这很可能就是改动前报告 §2.6 生产形态 3/7 的主要成因〔README §5e〕。
  * 修法是新开关 **`block_drift_rebuild`（默认开）**：用**重排器**问一句"当前块里有没有真能回答这个问题的内容"，块内优先级最高的 ≤128 块（每块截 600 字符）重排，最高分都答不上（`block_relevance_min=0.30`）就重建〔`rag_proxy.py:1114-1124`〕。
  * **为什么必须用重排器而不是嵌入余弦**（试错过，务必保留）：嵌入余弦比"全历史最好的块 vs 块内最好的块"**分不开句式相同的事实块**——实测 `the pod code is …` 0.70 vs `the vault code is …` 0.48，块里塞满填充后差距更小 → 23 次组装只触发 1 次重建，召回只有 **2/6**；重排器是交叉编码器，同一组文档实测 **0.80 vs 0.0004**（差四个数量级）〔README §5e〕。
  * 实测对照〔README §5e〕：

    | 组装块策略 | 召回 | 判据触发的重建 | 已覆盖的追问 |
    |---|---|---|---|
    | TTL 内无脑复用（改动前行为） | 0/6 | — | 复用 |
    | 每问都重建（TTL=0） | 6/6 | 每次都重建（前缀缓存全丢） | 重建 |
    | **覆盖度判据（现在默认）** | **6/6** | **6 次**（正好一问一次） | **仍复用**（0 次额外重建） |

* **配置项**：`structure_chunking`（false=退回旧分块，A/B 用）、`context_expand_ratio`（默认 0.25）、`block_drift_rebuild`、`block_relevance_min`、`block_check_docs`、`block_check_chars`〔`config.json:18-23`〕。
* **代价**：每个超窗请求多一次重排调用（≤128 块 × 600 字符，实测每个问题整轮 ~2s）；只有"块确实没覆盖这个问题"时才付重建的钱（= 前缀缓存失效，TTFT 秒级→分钟级）。

### 3.5 §5f 窗口守卫：不把必然 400 的请求放出去（2026-10-08）★本轮改动

* **动机（生产翻车原文）**：

  ```
  API Error: 400 prompt (231775 tokens) + max tokens (32000) exceeds the context (262144);
  requests are never truncated. Send a smaller max_tokens (at most 30361 here) … (#545)
  ```

  网关当时记的是 `ctx[组装]: 窗口 262144 = 提示词 219021（原始 316363 tok） + max_tokens 32000 + 边界 8 | 余量 43115`
  ——**网关以为还剩 43k，引擎自己数到 231,775，只剩 30,361**。差 **12,754 token（5.8%）**。引擎对超窗请求**直接 400、从不截断**，所以这道算术错一次就是一次客户端可见的失败〔README §5f〕。

* **做法（三条真实通路，全部补上）**：
  1. **旧估算不是上界**。旧公式 `len/1.5` 对**数字串**和**单字重复 CJK** 低估 1.5×。改动后按字符分类取**上界**：`tok_per_char_cjk=1.05`、`tok_per_char_digit=1.05`、`tok_per_char_other=0.70`，再加每消息模板开销 `msg_overhead_tokens=8`〔`rag_proxy.py:181-192`〕。快通道判据从 `est*2 < budget` 改成 **`est + 残差 ≤ budget`**〔`rag_proxy.py:1403-1417`〕。标定表〔README §5f〕：

     | 文本类别 | 实测 tok/char | 旧 est | 旧 est 相对真实 |
     |---|---|---|---|
     | 英文散文 | 0.188 | 0.667 | 高估 3.5× |
     | 工具 JSON | 0.266 | 0.667 | 高估 2.5× |
     | 代码 | 0.389 | 0.667 | 高估 1.7× |
     | 随机词 | 0.474 | 0.667 | 高估 1.4× |
     | 中文散文 | 0.506 | 0.667 | 高估 1.3× |
     | 中英混排 | 0.625 | 0.667 | ≈持平 |
     | **数字串** | **1.000** | 0.667 | **低估 1.5×** |
     | **单字重复 CJK** | **1.000** | 0.667 | **低估 1.5×** |

  2. **图片谁都没算**。`/v1/messages/count_tokens` 把一张图只数 1 个 pad，引擎 `prepare()` 展开成每图一个 token〔README §5f〕：

     | 请求 | count_tokens | 引擎 prepare | 差额 |
     |---|---|---|---|
     | 1 张 64×64 | 66 | 74 | +8 |
     | 1 张 512×384 | 66 | 358 | +292 |
     | 1 张 1024×768 | 66 | 297 | +231 |
     | **6 张 1024×768** | 161 | 4763 | **+4602** |

     现在 `image_tokens=1024` 每张，估算与精确计数两条路都算进去〔`rag_proxy.py:195-219`〕。
  3. **残差没留、砍无可砍就作罢**。`clamp_max_tokens` 现在余量再减 `clamp_margin_tokens(512) + prompt/64`〔`rag_proxy.py:222-245`〕；组装的收敛循环改成"砍最长消息头部 → 不够就丢最近窗口里最旧的整条消息"，**必须收敛到装得下**〔`rag_proxy.py:1183-1210`〕；降级透传也不再原样转发，先按上界估算压一次 `max_tokens`（`_guard_body`，`1320-1337`）。

* **最后一道网**（与上面三条独立）：引擎 400 原话里已写"这里最多还能给多少 max_tokens"，`_proxy` 认这句话，照它压小 `max_tokens` **重发一次**〔`rag_proxy.py:1297-1305`〕，客户端拿到正常回答而不是 400。计数器 `overfit_retries` / `overfit_failures`（后者=提示词本身就超窗，压输出救不了）。
* **实测对照**：离线回归 `test_window_guard.py` **40+ 断言全绿**〔README:252，原文"40+ 断言全绿，35s"；交接核对记录为 34s。**原始输出日志未留存**，见 §4〕。真引擎验收见 §4/§6——**只有网关侧结论可用**。
* **配置项**：`tok_per_char_cjk/digit/other`、`msg_overhead_tokens`、`image_tokens`、`clamp_margin_tokens`、`clamp_margin_div`、`retry_on_overfit`〔`config.json:25-32`〕。

### 3.6 本轮修复：并发串行化 + 查询入队去重 + 思考预算守卫（2026-10-08 下午）★已上线

#### 3.6.1 会话级串行锁 —— 同键并发不再交错

* **动机**：同一个会话键上两个在飞的请求共享同一份会话状态（历史序列 / 分块索引 / 向量表 / 计数前缀 /
  组装块）。实测到的三条交错后果：
  1. `ingest()` 没有会话级锁 → 同一内容可能入库两次、`idx` 可能重复（检索候选里多一份同样内容）；
  2. 分叉请求的 `reset()` 会把**在飞请求已经入库的块清掉**，那个在飞的组装随后检索到的是**对方**灌进来的块；
  3. `count_hashes` 与 `count_total` 是分两步赋值的，并发下可能读到"新的哈希序列 + 旧的总数"。
* **做法**：`Session` 加一把 `threading.RLock`〔`rag_proxy.py` `Session.__init__`〕；`_rag_request` 从**历史守卫**
  到**组装结束**整段持锁，**转发放在锁外**（上游是几十秒的长尾，不该占着锁）〔`rag_proxy.py:1438-1521 区段`〕。
* **实测对照**（离线 `test_concurrent_session.py`，用"assemble 替身睡 1 秒"把时序做成确定的）：
  同键并发的第二个请求耗时 **2.01s**（= 等第一个出锁 + 自己走一遍），异键 **1.02s**（不被挡）；
  并发分叉被判出 `session reset: history diverged at message 1/4 (key hdr:sess-D)`。
  **反证**（`test_concurrent_session_nolock.py`，把 `self.lock` 换成 `contextlib.nullcontext()` = 改动前行为）：
  同键 **1.02s、该判据失败**，其余不变 → 证明这条判的就是这把锁。
  *诚实备注*：**分叉判定那一项不判别锁**——守卫在 assemble 之前就发布了历史，没有锁时它同样通过
  （已实测）。锁真正消除的是上面第 2 条路径。
* **代价**：同会话并发被排队（一个会话本来就是顺序的）；最坏情况第二个请求要等第一个走完组装
  （组装里有 `embed_wait_s=120` 的有界等待）。
* **配置项**：无。**回滚**：把 `with sess.lock:` 去掉，或照 `test_concurrent_session_nolock.py` 把锁换成空操作。

#### 3.6.2 查询向量入队去重 —— 防"拿空串嵌入"

* **动机**：查询向量入队原来不在 `EMB_LOCK` 内、也不查 `EMB_SEEN`。两个并发同查询请求会各入队一次；
  第二次出队时文本已被前一次 `pop` 掉 → 拿**空串**去嵌入，并把结果覆盖进 `EMB_CACHE[qh]`——此后这个
  查询的向量一直是错的（检索质量下降）。worker 侧也没有兜底。
* **做法**：入队挪进 `EMB_LOCK` 并与 `EMB_SEEN` 去重；worker 侧跳过"文本已被取走"的条目，绝不拿空串去嵌入
  〔`rag_proxy.py` 的 `build_memory_block` 查询入队段与 `embedding_worker`〕。
* **实测对照**：相关路径在 `test_window_guard.py` / `test_thinking_guard.py` 端到端下全绿；
  **没有**构造"并发同查询"的专门用例——列入未决（§8 第 17 项）。
* **配置项**：无。**回滚**：去掉 `EMB_SEEN` 的去重判断。

#### 3.6.3 思考预算守卫 —— "想完了却没有答案"

* **动机**（本轮最重要、**真实用户可见**的一条）：引擎的思考预算是 **opt-in、默认不限**，思考会一路吃到
  `max_tokens` 耗尽，答复阶段一个 token 都不剩。引擎自己的诊断原文：

  ```
  [strata] the reply reached max tokens while still thinking, so it has no answer: a thinking budget
  (reasoning_budget_tokens, in the request or in strata-<model>.json for every request) leaves room to answer
  ```

  〔`~/deploy/logs/strata-a.out.log:22473`；对应 `serve/server.py` 的 #530〕。实测规模：

  | 引擎 | 事件数 | 发生时的 `max_tokens` 分布 |
  |---|---|---|
  | `strata-a` | **173** | **2112 × 149**、32000 × 14、512 × 5、256 × 2、200 × 1、32768 × 1、32 × 1 |
  | `strata-b` | **81** | **512 × 49**、2048 × 11、16384 × 4、2000 × 1、64 × 1、32 × 2、16 × 1、10 × 2、8 × 2、4 × 4、1 × 4 |

  〔`grep -ac 'reached max tokens while still thinking' ~/deploy/logs/strata-{a,b}.out.log`〕
  **`max_tokens` 小的客户端受害最重**（2112 一档就占 149 次）——所以"在引擎配置里设一个固定预算"救不了他们
  （预算一超过他们的 `max_tokens` 就没用），**必须按请求给**。
* **做法**：客户端**没有表达过思考偏好**时，网关补一个思考预算 = `max_tokens - 预留`，
  预留 = `min(answer_reserve_tokens, max(64, max_tokens // answer_reserve_div))`。客户端一旦给了
  `thinking` / `output_config` / `reasoning_effort` / `reasoning_budget_tokens`，**一个字节都不碰**。
  引擎收到该参数后在到达预算时**自己收尾**（`serve/server.py:1816-1826` 注入 `REASONING_WRAP_UP`：
  `"I have thought about this long enough; time to give my answer."` + `</think>`）并接着生成——
  **已经读进去的前缀不重读**，代价只是"思考短一点"，不是重来一遍 prefill。
* **为什么用"预留"而不是固定比例**：正常流量根本碰不到——`max_tokens=32000` 的请求预算给到 **27904**，
  实测本机 Claude Code 一轮思考 2,090 token（占比 6.5%）完全不受影响；只有"思考要吃掉几乎全部额度"的
  病态请求才会被收拢。`max_tokens=2112` → 预算 1408（留 704 给答复）；`512` → 342；
  小于 128 的（留不出答复空间）**不补**。
* **实测对照**（离线端到端 `test_thinking_guard.py`，断言落在"引擎到底收到了什么"）：
  | 客户端请求 | 引擎实际收到 |
  |---|---|
  | `max_tokens=2112`，无思考字段 | `reasoning_budget_tokens=1408`，**其余字段逐字段相同** |
  | `max_tokens=2112` + `thinking: {budget_tokens: 1024}` | **无注入**，body 逐字段相同 |
  | `max_tokens=2112` + `reasoning_budget_tokens=900` | 原样 900，**未被覆盖** |
  | `max_tokens=64` / 无 `max_tokens` | 不补 |
* **真引擎预检**（2026-10-08 13:25–13:28，**在临时端口 8083 上另起一个独立实例**，两条极小请求打 `strata-b`；
  受托管的生产进程 pid 651006 全程未动，预检后 8083 已释放）：

  | 检查什么 | 结果 | 来源 |
  |---|---|---|
  | 引擎**接受**注入的字段吗（会不会 400） | HTTP **200**，正常回答；代理日志 `ctx[透传(快通道·上界估算)]: … 余量 261603 思考预算 1408` | `/tmp/preflight-1.out.log` |
  | 引擎**照它收尾**吗 | 引擎日志出现 **`[strata] thinking budget reached (1408 tokens): wrapping up the thinking`**（该文件此前 **0 次**——说明至今没有任何客户端或配置给过思考预算），随后给出完整回答、`finish_reason=stop` | `~/deploy/logs/strata-b.out.log` |

* **上线后的生产观测**（2026-10-08 13:47–13:48，重启后立刻出现）：`ctx[...]` 行已经带注入值——
  `提示词 11761 + max_tokens 16384 … 余量 249680 思考预算 12288`（= 16384 − 4096）、
  `提示词 847 + max_tokens 2048 … 余量 260764 思考预算 1366`（= 2048 − 682）；
  同一批流量里**带 `thinking` 的客户端请求没有这个字段**（尊重客户端）〔`~/deploy/logs/rag-proxy.out.log`〕。
* **一处自查发现的缺口（13:48 修，✅ 15:20:18 随重启上线）**：`max_tokens` 被窗口守卫压小之后，补的思考预算
  可能比它还大（那就等于没有预算，思考照样吃满）。新增 `refit_thinking_budget()`〔`rag_proxy.py:287-305`〕：
  **只重算网关自己补的那个**（客户端自带的绝不碰），`max_tokens` 变小时按同一规则重算，留不出空间就不带。
  实测：`max_tokens=26228` + 预算 `27904` → **22132**；`300` → `200`；`64` → 不带；本来就比上限小的不动
  〔`test-logs-1008/test_thinking_guard.log` 的 A2 组〕。这条正落在 §5f 的高压区——23 万 token 的提示词会把
  `max_tokens` 从 32000 压到 ~26228（引擎原话 `at most 30361 here`）。
* **一处配置细节**：`answer_reserve_tokens` 之上还有 `answer_reserve_div` 封顶（预留 ≤ `max_tokens/3`）。
  对 `max_tokens=2112` 来说预留恒为 **704**，把 `answer_reserve_tokens` 从 4096 调到 1900 **不改变结果**
  （预检时实测：注入值仍是 1408）——要改这一档的预留，得调 `answer_reserve_div`。
* **配置项**：`thinking_budget_guard`（默认 **true**）、`answer_reserve_tokens`（4096）、`answer_reserve_div`（3）。
  **观测**：`ctx[...]` 行尾会多出 ` 思考预算 N`（网关补的与客户端自带的都会写出来）。
* **回滚开关**：`thinking_budget_guard: false` → 完全不碰任何请求（回到改动前行为）。
* **另一条可选路线（未采用）**：在 `strata-iq3_xxs-a.json` / `-b.json` 顶层加 `"reasoning_budget_tokens": N`
  （引擎支持：`serve/server.py:3277` 读它，启动时打印 `[strata] thinking budget: N tokens`）。
  缺点是固定值对小 `max_tokens` 客户端无效、且要重启引擎；请求级参数（本方案）能随 `max_tokens` 自适应，
  并且尊重客户端自己的选择。
* **一处耦合要注意**：引擎若被改成 `anthropic_thinking: "on_request"`，请求里带 `reasoning_budget_tokens`
  会被当作"客户端要思考"（`serve/frontend.py:248-256`）。当前配置是默认的 `"model"`（思考本来就开），
  所以不受影响；将来若切到 `on_request`，要么关掉本守卫，要么接受"未表态的客户端也会思考（但有预算）"。

### 7.4 `ctx[...]` 行怎么读

格式（`log_ctx()`，`rag_proxy.py:320-340`）：

```
ctx[模式]: 窗口 262144 = 提示词 <本次进引擎的提示词 tok>（原始 <客户端原始 messages tok>） + max_tokens <最终值>
          + 边界 8 + 计数残差 <margin> | 余量 <剩余> 最近窗口 <逐字窗口 tok> + 检索块 <检索块 tok>·块复用
          思考预算 N                        ← 客户端自带的、或 §3.6.3 网关补的，都会写出来
          ⚠ max_tokens 超余量已压到 N        ← 只有发生压缩时才有
```

模式只有四种：`透传(快通道·上界估算)`、`透传(精确计数)`、`组装`、`组装(计数不可用·上界估算)`，以及降级时的 `透传(降级·上界估算)`。
生产实录（新格式带"计数残差"，可用来确认跑的是 §5f 之后的代码）：

```
[12:46:25] ctx[透传(快通道·上界估算)]: 窗口 262144 = 提示词 648 + max_tokens 2048 + 边界 8 + 计数残差 522 | 余量 260966
[12:29:43] ctx[组装(计数不可用·上界估算)]: 窗口 262144 = 提示词 217402（原始 339471 tok） + max_tokens 32000 + 边界 8 + 计数残差 3908 | 余量 40826 最近窗口 38796 + 检索块 54654
[12:29:30] ctx[透传(降级·上界估算)]: 窗口 262144 = 提示词 339356 + max_tokens 1 + 边界 8 + 计数残差 5814 | 余量 -83034 | ⚠ max_tokens 超余量已压到 1
```

读法要点：**"原始 X tok"是客户端给的量，"提示词"才是这次真正发出去的**；"余量"已经把 `max_tokens`、边界 8、计数残差都扣掉；看见 `⚠` 就是这条请求的输出预算被网关压过。

## 8. 已知限制与未决问题

**结构性限制（设计如此）**

1. **全内存、无持久化**：进程重启（含 pod 重建）后嵌入/重排/组装/会话缓存全部清空，会话要重新"渐进"一轮〔README §7〕。
2. **跨会话不共享缓存**：嵌入缓存是全局的，但**检索**按会话索引，跨会话不互相召回〔README §7〕。
3. **图片不嵌入内容**：只记占位符；现在只保证"token 账算得对"（`image_tokens=1024`/张），不理解图里是什么。
4. **鉴权由客户端自带 key**：网关只透传，不为无 key 请求补 key（这是刻意的，见 §0.3）。
5. **`:8081` 与 `:8080` 一样对 pod 外可访问**；若要对外提供，建议在网关前再套一层鉴权〔README §7〕。

**精度天花板（改动前基线，改动后未重测）**

6. **1M 本质是检索精度**：引擎原生窗 262,144，对外 1M 由网关组装（最近 65536 逐字 + 检索块）。"找一条清晰事实"任意深度接近 100%（NIAH 15/15、外网出口 3/3）；**"多条相似事实散落召回"是真实短板**（BABILong 2/15、生产形态 3/7），且失败模式包含**自信地答错**（§2.6 里 `pod@40` 答成 `COBALT-3141`、`harbor@150` 答成 `MEADOW-2718`）〔报告 §2.6/§2.7〕。
7. **`rag_1m_test.py` 的 1M 是名义 1M**：`chars = tok_per_turn * 1.5`，中文（实测 0.506 tok/char）下实际约 2,500 tok/轮，300 轮 ≈ **750k 而非 1M**。引用 token 数必须用网关 `ctx[...]` 日志里的真实值，不要引用脚本目标值。
8. **`/metrics` 的 `requests[0]` 不能用来断言单次请求**：它是引擎"最近一条"，混着别的会话和网关自己的 `count_tokens`。真引擎验收必须读响应自带的 `usage`。10-08 那份 `G.log` 就栽在这上面（出现"260,751 tok 的请求引擎只数到 153"、两档都恰好 38,151 这种荒谬值，**引擎侧数字整体不可用**）。
9. **同一份 `G.log` 的构造器没收敛到目标**：`228,159`（目标 231,775）、`195,567`（目标 200,000）。后果是那两档**当时什么都没测到**——`228,159+32,000+8 = 260,167 ≤ 262,144`，`195,567+60,000+8 = 255,575 ≤ 262,144`，本来就没超窗（直连 8092 也确实 200）。

**未决（按重要性）**

10. **§3.6 已全部上线**（13:47:15 + 15:20:18 两次重启）。剩下的是"病根级"的两件：
    ① `strata-b` 上 `done: 1/4/8/32 tokens (length)` 那批（55/44/19/14 次）与 `strata-a` 上的 2112 一档，
    根子在**客户端把 `max_tokens` 定得太小**——守卫只能保证"答复有一份"，给不了"够写一份"；
    ② R3（查询入队竞态）**没有专门的并发用例**（§8 第 16 项）。
11. **§5f 的真引擎验收：strata-a 已跑（14:43，ALL PASS），strata-b 待重跑。**

      （`at most 30314 / 12108 / 1104 here`，其中第一档正是生产翻车那句的同款）；四档都满足 `引擎 prompt + 送出 max_tokens + 8 ≤ 262144`。
